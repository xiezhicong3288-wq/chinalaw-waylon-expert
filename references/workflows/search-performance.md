# 检索性能与缓存维护

普通使用直接执行 `scripts/search_law.py`，无需阅读本文件。JSON 目录、索引和 Markdown 原文仍是唯一维护入口；不要手工修改数据库。

## 按需读取

- 条文查询先运行脚本，避免把整份目录、索引或法律全文放进对话。条号查询输出完整条文；关键词摘要需再定位完整条文。
- 能确定法律时使用 `--law`；初步检索设置较小的 `--limit`，没有足够依据时再扩大范围。返回数量上限不证明相关法源已经穷尽。
- 办案按争点和阶段加载流程。法律细节见 `law-routing.md`；全案步骤见 `case-method.md`。不要把新增专题全文持续加入 `SKILL.md`。

## 可丢弃的本地缓存

首次关键词检索在 Skill 下的 `.cache/law-search.sqlite3` 建库，首次或资料变更后的关键词查询会支付建库成本。已知法律和条号时直接查 JSON 索引与 Markdown 原文，不为单条查询构建或检查整库缓存；显式使用 `--rebuild-cache` 时仍会重建。后续关键词检索复用 SQLite 候选索引；命中的条文仍从 Markdown 读取，缓存不充当引用原文。

支持 FTS5 trigram 的 Python/SQLite 会对至少三个字符的关键词使用三字符索引，再以原有子串规则核对；一两个字符的中文词或不含 FTS5 的环境使用 SQLite 子串扫描。别名扩展、索引顺序、条号增补和结果数量含义保持不变。全库短词仍随数据量增长，不能声称所有查询都是常数时间。

每次使用关键词缓存时检查目录、索引、检索代码和原文文件的属性及 SHA-256 内容指纹；变化后原子重建，损坏缓存也重建。即使同步工具恢复了文件时间与大小，内容变化也会使关键词缓存失效。指纹检查仍需读取相应文件，成本随数据量增长，但省去重复解析与分词；这是本地性能缓存，不是法律效力核验。

```text
python scripts/search_law.py --law 民法典 --article 577 --rebuild-cache
python scripts/search_law.py --law 民法典 --article 577 --no-cache
```

缓存目录不可写、SQLite 出错或构建失败时，标准错误流提示回退，继续用 JSON 和 Markdown 检索。只读安装环境可以直接用 `--no-cache`。原文缺失时不会用缓存正文代替原文。

缓存忽略于 Git，打包器也排除 `.cache/`，不需要提交或随 ZIP 发布。维护时仍运行结构校验和测试；缓存有效只表示与本地资料一致，不证明当前法律效力。

## 可复现测量

`scripts/benchmark_search.py` 对同一组条号、限定法律关键词、全库长短词和未命中查询分别测试 `--no-cache` 与默认路径，核对退出码、标准输出和错误输出一致，再报告每次启动独立 Python 进程的耗时中位数与首次强制重建耗时。精确条号查询的默认路径直接读取索引；关键词默认路径使用缓存。首次重建单列，不混入复用中位数。

```text
python scripts/benchmark_search.py --runs 7
```

这是本地检索工具测量，不是整轮 AI 回答速度；联网核验、推理、输出长度和主机负载会另行影响使用体验。
